1. PURPOSE OF THIS FILE
===============================================================================

This file is the self-contained technical handover for the repository. It
records what exists, how the pieces connect, what has been verified, what is
currently only present in the working tree, and what remains to be integrated
or tested. A new team member should read this file before changing firmware,
wiring, the Bluetooth protocol, or the desktop tools.

The project currently consists of four main areas:

1. Teensy 4.0 firmware managed by PlatformIO.
2. A live Bluetooth/serial robot-debugging GUI.
3. Recording, visualisation, and command-line analysis tools for saved runs.
4. A collection of supplied hardware example sketches used as references.

The newest work makes the debug GUI data-driven. GUI parameter and command
controls are described in one JSON file. The PlatformIO build validates and
embeds that JSON, while a firmware library handles the complete serial workflow.

2. CURRENT HARDWARE COMMUNICATION LAYOUT
===============================================================================

Controller:

- Teensy 4.0.
- Firmware framework: Arduino through PlatformIO.
- Firmware environment name: teensy40.

Bluetooth debug connection:

- Hardware: supplied, pre-matched CH9143 Bluetooth serial board pair.
- One board plugs into the robot carrier board.
- The other board connects to the computer through USB-C.
- The pair behaves as a transparent serial cable. The desktop software sees a
  conventional Windows COM port and does not implement a separate radio layer.
- Robot-side connector: SERIAL1.
- Teensy UART: Serial1.
- Teensy Serial1 pins: RX1 pin 0 and TX1 pin 1.
- Baud rate: 115200.
- Framing: 8 data bits, no parity, 1 stop bit.
- Application framing: one JSON object followed by a newline.
- During verified testing, Windows identified the receiver as
  "USB-BLE-SERIAL CH9143" on COM10.
- During the same testing, COM7 was the Teensy's direct USB programming port.
- COM numbers are assigned by Windows and may change. Select the device by its
  description instead of relying permanently on COM10.

Herkulex smart-servo connection:

- Bluetooth now occupies SERIAL1.
- The Herkulex bus is therefore configured to use Teensy Serial2.
- The Herkulex cable must be plugged into the carrier board's SERIAL2 connector.
- Servo UART baud rate: 115200.
- Sorting-gate default ID: 1.
- Kicker-cam default ID: 2.
- Accepted position-command range: approximately -160 to +160 degrees.
- Movement time accepted by the debug command: 50 to 2850 ms.
- Startup, STOP, and leaving Debug Mode disable broadcast servo torque.

Important configuration inconsistency to clean up:

- PlatformIO/include/config.h correctly assigns HerkulexConfig::PORT to
  Serial2 and BluetoothConfig::PORT to Serial1.
- The older Pins::SMART_SERVO_RX and Pins::SMART_SERVO_TX constants and nearby
  comments still say pins 0 and 1. Those constants are stale and conflict with
  the current Serial2 assignment. The active workflow uses the HardwareSerial
  object, so the working code is not using those stale constants, but the names
  and comments should be corrected before other firmware starts depending on
  them.

Other configured hardware assignments:

- Drive left PPM: pin 2.
- Drive right PPM: pin 3.
- Reel left PPM: pin 4.
- Reel right PPM: pin 5.
- Front ultrasonic trigger: pin 9.
- Front ultrasonic echo: pin 10.
- Inductive proximity input: pin 11.
- Left analogue IR: A0.
- Right analogue IR: A1.
- TOF sensor bus: Wire / I2C bus 0.
- Colour sensor bus: Wire1 / I2C bus 1.
- SX1509 expander address: 0x3F.
- Runtime-configured point TOF addresses use 0x40 through 0x47.

Several values in config.h are explicitly placeholders. Sorting-gate angles,
kicker angles, sensor counts, XSHUT expander pins, and the analogue IR presence

5. JSON-DRIVEN GUI CONFIGURATION
===============================================================================

Human-edited source file:

    PlatformIO/debug_config.json

Generated build file:

    PlatformIO/include/debug_config.generated.h

Generator:

    PlatformIO/scripts/embed_debug_config.py

Detailed editing guide:

    PlatformIO/DEBUG_GUI_CONFIG.md

Build process:

1. PlatformIO runs embed_debug_config.py before compiling firmware.
2. The script reads debug_config.json using Python's strict JSON parser.
3. Invalid JSON stops the build and reports the editing error early.
4. Valid JSON is compacted.
5. The compact JSON is written into debug_config.generated.h as a C++ string.
6. The BluetoothDebugWorkflow library parses the embedded string during Teensy
   startup.
7. When the desktop GUI connects, the library advertises every configured
   parameter and command.

Do not edit debug_config.generated.h manually. Any manual edit will be replaced
on the next PlatformIO build.

Current JSON parameters:

- debug.telemetry_interval_ms
  - Label: Telemetry interval.
  - Type: integer.
  - Unit: milliseconds.
  - Default: 200 ms, giving 5 telemetry updates per second.
  - Minimum: 50 ms.
  - Maximum: 2000 ms.
  - Step: 50 ms.
  - This parameter is connected to live behavior; changing it changes the
    actual firmware telemetry period.

Current JSON commands:

- ping
  - Action: ping.
  - No arguments.
  - Returns "Pong from Teensy" as a log and sends current state.

- stop
  - Action: stop.
  - No arguments.
  - Broadcasts torque-off to the Herkulex bus.
  - Sets stopped state true.
  - Sends state and a warning log.

- run
  - Label: Run Robot.
  - Action: run.
  - Requires Debug Mode.
  - Clears stopped mode without moving or energising a servo by itself.
  - A relative movement command remains necessary before torque is enabled.

- set_herkulex_angle
  - Label: Set Herkulex angle.
  - Action: herkulex_angle.
  - Requires Debug Mode.
  - Arguments:
      id: integer from 1 through 253, default 1.
      angle_deg: numeric from -160 through +160, default 0.
      move_time_ms: integer from 50 through 2850, default 500.
  - Clears the selected servo's errors, enables its torque, sends the movement,
    updates commanded-position telemetry, and reports running state.

- read_herkulex_angle
  - Label: Read Herkulex angle.
  - Action: herkulex_read_angle.
  - Argument: servo ID from 1 through 253, default 1.
  - Requests position feedback from the selected servo.
  - Publishes a valid result as servo.measured_angle_deg telemetry.
  - Reports an error if no valid response packet is received.
  - The first successful manual read enables automatic reads for that servo ID
    every 200 ms until the Teensy resets.

- zero_herkulex_here
  - Label: Zero Herkulex here.
  - Action: herkulex_zero_here.
  - Argument: servo ID from 1 through 253, default 1.
  - Reads the current physical position without moving the servo.
  - Stores that position as the temporary software-zero offset for that ID.
  - All later movement angles for that ID are interpreted relative to this zero.
  - The offset is held in RAM and is cleared by reset or power loss.
  - Movement is rejected until the selected servo has been zeroed.

What is automatic when editing JSON:

- Adding a parameter object creates a GUI parameter control.
- Removing a parameter object removes that control.
- Numeric parameter changes are validated, clamped to JSON min/max values,
  held in Teensy RAM, and confirmed to the GUI.
- Adding a command object creates a GUI command control.
- Removing a command object removes that control.
- Command arguments generate the appropriate integer/float/boolean/string/enum
  controls supported by the desktop GUI.
- Setting debug_mode_required protects a command until Debug Mode is enabled.
- Selecting an already implemented action connects the GUI command to that
  firmware behavior.

What is not possible from JSON alone:

- JSON can describe a control and select an existing action, but it cannot
  invent new electrical or mechanical behavior.
- A completely new action name requires one matching C++ implementation in
  BluetoothDebugWorkflow.cpp.
- A generic parameter is stored and displayed automatically, but using it in a
  new drivetrain, sensor, or control algorithm requires that algorithm to read
  or bind the value.
- Parameter values are currently temporary and return to JSON defaults after a
  Teensy reset. Persistent EEPROM/configuration storage has not been added.

6. BLUETOOTH DEBUG WORKFLOW LIBRARY
===============================================================================

Files:

    PlatformIO/lib/BluetoothDebugWorkflow/BluetoothDebugWorkflow.h
    PlatformIO/lib/BluetoothDebugWorkflow/BluetoothDebugWorkflow.cpp

Responsibilities:

- Start the Bluetooth UART.
- Start the Herkulex UART.
- place Herkulex servos in safe torque-off state at startup.
- Parse the embedded GUI configuration.
- Process incoming desktop messages.
- Advertise parameter and command definitions.
- Apply and confirm parameter changes.
- Route configured commands to built-in actions.
- Enforce Debug Mode for protected commands.
- Send state, logs, errors, and periodic telemetry.
- Pace definition messages to avoid overflowing the CH9143 radio link.
- Suppress duplicate startup definition bursts.

Incoming computer-to-robot message types handled:

- hello.
- request_definitions.
- command.
- parameter.
- parameter_request.

Outgoing robot-to-computer message types produced:

- telemetry.
- parameter_definition.
- parameter_value.
- command_definition.
- log.
- state.
- error.

Startup behavior:

1. Bluetooth Serial1 opens at 115200.
2. Herkulex Serial2 opens at 115200.
3. Broadcast torque-off is sent to servo ID 0xFE.
4. Embedded JSON is parsed.
5. The configured telemetry interval is loaded.
6. A ready log and safe state are transmitted.

Connection behavior:

1. Desktop sends hello.
2. Firmware sends a connected log and current state.
3. Firmware immediately sends definitions.
4. Desktop also sends request_definitions.
5. Firmware suppresses that request if definitions were sent within the last
   500 ms, avoiding duplicate traffic during radio startup.

The immediate advertisement was added because physical testing showed that the
matched bridge could occasionally deliver hello but lose the next back-to-back
request. Definition packets are separated by 40 ms, and normal telemetry is
limited to 5 Hz by default. This eliminated observed packet corruption without
requiring RTS/CTS wiring.

Current telemetry signals:

- system.uptime_s.
- system.debug_mode.
- system.stopped.
- bluetooth.messages_received.
- servo.last_id.
- servo.commanded_angle_deg.
- servo.measured_angle_deg, after the first successful angle read.
- servo.zeroed.
- servo.zero_offset_deg, after the selected servo has been zeroed.
- servo.auto_read_enabled.
- servo.responding.
- servo.tracking_fault.
- servo.position_error_deg, once a target and measurement are available.

Commanded angle records the most recent movement request. Measured angle records
position feedback returned by the servo and remains absent until a read succeeds.
Once zeroed, both commanded and measured angles are relative to the stored zero.
Absolute targets are checked against the servo's +/-160 degree protocol range.
Automatic monitoring tolerates individual packet losses. Three consecutive
read failures mark the servo unresponsive and set fault state. After a movement
has had its requested duration plus 300 ms to settle, three consecutive readings
more than 8 degrees from target set a tracking fault. Recovery clears the fault.

7. LOW-LEVEL ROBOT DEBUG SERIAL LIBRARY
===============================================================================

Files:

    PlatformIO/lib/RobotDebug/RobotDebug.h
    PlatformIO/lib/RobotDebug/RobotDebug.cpp

Responsibilities:

- Maintain a fixed receive buffer for serial bytes.
- Reassemble messages that arrive over several UART reads.
- Use newline as the packet boundary.
- Ignore carriage returns.
- Reject lines exceeding 767 bytes.
- Parse JSON with ArduinoJson.
- Reject malformed JSON and non-object JSON values.
- Call the workflow's message handler with an instance context pointer.
- Serialize outgoing JSON followed by a newline.
- Provide helpers for logs, errors, state, and parameter confirmations.

The callback was refactored to carry a context pointer. This allows the reusable
BluetoothDebugWorkflow instance to receive parsed messages without putting
application routing in main.cpp or relying on a global singleton.

9. SENSOR LIBRARIES
===============================================================================

IR library:

    PlatformIO/lib/Ir/Ir.h
    PlatformIO/lib/Ir/Ir.cpp

The project includes an IR abstraction. The configuration notes record that
analogue distance readings were too noisy for dependable ranging, especially
off-angle. The intended use is therefore object-presence detection with a raw
ADC threshold. The current configured threshold is 400 and requires tuning on
the installed sensors.

TOF library:

    PlatformIO/lib/Tof/Tof.h
    PlatformIO/lib/Tof/Tof.cpp

The project includes support structure for Pololu VL53L0X short-range and
VL53L1X long-range sensors, with shutdown lines intended to be controlled by an
SX1509 I/O expander. Address allocation and sensor counts are configured in
config.h. Final physical sensor count, bus layout, expander pins, and mounting
still require confirmation.

Neither sensor library is currently integrated into the minimal main program or
the active Bluetooth telemetry set.

18. HERKULEX DRS-0101 CONTINUOUS-VELOCITY CONTROL
===============================================================================

Continuous-turn support has now been added to the reusable Herkulex and
Bluetooth debug libraries. The DRS-0101 does not treat infinite rotation as a
position beyond its approximately 320-degree position-control range. It uses a
separate turn/velocity mode. The firmware therefore keeps position commands and
continuous-velocity commands as distinct operations.

The HerkulexTeensy library now exposes moveVelocity(). Its signed speed input is
limited to -1023 through +1023. The magnitude selects the requested drive level;
the sign selects direction. A speed of zero requests no rotation. The outgoing
S_JOG packet sets the DRS turn-mode bit and encodes negative direction with the
protocol's direction flag.

Two JSON-defined GUI commands were added:

- Set continuous velocity: accepts servo ID and signed speed.
- Stop continuous rotation: accepts servo ID, sends zero speed, and removes
  torque.

Set continuous velocity requires Debug Mode and the Run Robot state. The
suggested first test is a low magnitude such as +100 or -100 with the mechanism
clear. The firmware changes modes using the safe sequence required by the servo:
torque off, clear errors, send a zero-speed turn-mode command, torque on, then
send the requested velocity. The position command follows the corresponding
torque-off mode-switch sequence before executing a position move.

The ordinary STOP command also cancels the stored continuous-rotation state and
removes servo torque. While continuous rotation is active, position tracking
fault checks are suspended because a continuously turning shaft does not have a
fixed target. Automatic angle reads may continue, and telemetry now includes:

- servo.continuous_velocity_active
- servo.commanded_velocity

Zero Here is rejected while the selected servo is actively in continuous mode.
Stop Continuous Rotation first, then read/zero or issue position commands.

Recommended continuous-turn test sequence:

1. Ensure the mechanism can rotate freely.
2. Connect the desktop GUI to the CH9143 Bluetooth serial port at 115200 baud.
3. Enter Debug Mode.
4. Press Run Robot.
5. Use Set continuous velocity with speed +100 or -100.
6. Confirm the direction and telemetry.
7. Press Stop continuous rotation before changing operating modes.

Verification completed on 14 September 2026:

- The Teensy 4.0 firmware compiled successfully in PlatformIO.
- The resulting firmware uploaded successfully to the Teensy through COM7.
- The non-actuating COM10 smoke test passed after the GUI released the port. It
  received the Bluetooth handshake, parameter and command definitions, state,
  logs, and telemetry. Both continuous-turn commands were present.
- smoke_test.py now retains partial serial data across timeouts. This prevents a
  slow wireless frame from being incorrectly treated as a complete JSON line.
- The CH9143 link was observed intermittently losing catalogue frames while
  continuing to deliver telemetry. The desktop GUI now loads the shared
  PlatformIO/debug_config.json directly at startup, so parameter and command
  controls are always present. Definitions received wirelessly remain supported
  and update the already-created controls.

19. 203 DC MOTOR CONTROLLER ON SERIAL3
===============================================================================

Support for the 203_DCMotor controller has been added as a reusable library and
integrated into the Bluetooth debug workflow. Although it is plugged into the
SERIAL3 connector, it does not use UART messages. Its two channels expect
repeating servo-style control pulses. Teensy TX3/pin 14 controls channel A and
RX3/pin 15 controls channel B.

The DcMotor203 library implements the documented pulse range:

- -100 percent: 1050 microseconds, full reverse.
- 0 percent: 1500 microseconds, stopped/neutral.
- +100 percent: 1950 microseconds, full forward.

Intermediate signed percentages are mapped linearly. Both inputs are clamped to
-100 through +100. begin() attaches both pulse outputs and immediately commands
neutral, so startup does not deliberately turn either motor.

The JSON catalogue now creates Set 203 DC motor speed and Stop 203 DC motor
controls. Motion requires Debug Mode and Run Robot. The dedicated motor stop,
global STOP, and leaving Debug Mode all write the 1500-microsecond neutral pulse.
Run Robot only clears stopped mode and never starts the motor itself.

Telemetry fields are:

- dc_motor_203.active
- dc_motor_203.channel_a_percent
- dc_motor_203.channel_b_percent
- dc_motor_203.channel_a_pulse_us
- dc_motor_203.channel_b_pulse_us

The firmware compiled and uploaded successfully to the Teensy through COM7 on
14 September 2026. Physical rotation was not commanded during verification.

The initial integration incorrectly treated the board as a single-channel
controller and drove only TX3/pin 14. Comparison with PROVIDED EXAMPLE
CODE/203_DCMotor/203_DCMotor.ino showed that the supplied controller exposes two
independent servo-pulse channels. This was corrected on 14 September 2026:

- Channel A uses TX3/pin 14.
- Channel B uses RX3/pin 15.
- Two Servo objects are attached with plain attach(pin), matching the example.
- The speed control now accepts channel_a_percent and channel_b_percent.
- Stop and startup write 1500 microseconds to both channels.
- Telemetry reports the percentage and pulse width for each channel separately.

The corrected two-channel firmware compiled and uploaded successfully to COM7.

The controller location was subsequently corrected by the operator: it is on
SERIAL7, not SERIAL3. The final channel mapping is therefore channel A on
TX7/Teensy pin 29 and channel B on RX7/Teensy pin 28. Configuration, direct test
code, and debug-workflow motor code all use these shared corrected pin constants.

For direct bench diagnosis, PlatformIO/src/main.cpp was temporarily changed to
bypass the Bluetooth debug workflow. It creates DcMotor203 directly, holds both
channels at neutral for two seconds during startup, then commands channel A and
channel B to +25 percent continuously. This diagnostic build must not be flashed
unless both motors are mechanically clear. Restore the BluetoothDebugWorkflow

The first direct-test build was compiled but deliberately not uploaded. After no
motion was reported, main.cpp was changed again to reproduce the supplied
203_DCMotor example exactly on Serial3's two Teensy signals: both channels at

After the direct motor test, main.cpp was restored to the normal minimal

The reusable 203 motor integration and corrected Serial7 pin mapping remain in

The 8x8 TOF page gained a Raw/Fused view selector. Raw displays the exact 64
sensor measurements. Fused retains the same 8x8 dimensions but combines each
zone with agreeing cardinal neighbours and its previous-frame value using
weighted averaging. Depth-difference gates prevent blending across likely
object boundaries, and invalid measurements are not introduced into valid
zones. Switching the selector immediately redraws the latest received frame.
The updated desktop source passed Python bytecode compilation and repository
whitespace validation.

The earlier fused-grid interpretation was replaced after clarification. The
view selector now offers Raw grid and Smoothed image. Raw grid retains all 64
numeric cells. Smoothed image converts the same 8x8 distance colours into an
enlarged bilinearly interpolated heatmap, producing the continuous blurry-image
appearance of a low-resolution thermal camera without claiming extra measured
spatial resolution.

A third 8x8 view, Stable detail, was added for dependable interpretation. It
maintains five raw frames and filters every physical zone independently using a
temporal median followed by conservative smoothing. Invalid samples can be
covered briefly by recent valid measurements, while changes more than 250 mm
nearer are accepted immediately so a newly appearing obstacle is not hidden by
old history. Farther jumps remain filtered so a single noisy reading cannot
make an obstacle disappear. No neighbouring zones are averaged, preserving measured boundaries.
The filtered map is displayed with the same smooth colour interpolation.

The recording Weight8x8.rdbg was analysed directly for matrix performance. It
contained 263 valid 8x8 frames across 65.20 seconds, averaging 4.02 Hz. The
median frame interval was 0.249 seconds and the longest was 0.319 seconds. A
typical frame contained all 64 valid zones and the minimum was 63. Consecutive
valid measurements had a median absolute change of 0 mm and a 95th percentile
of 72 mm; 2.86 percent changed by more than 250 mm. The scene changed strongly
throughout the test, including an object approaching from roughly 304 mm to
74-91 mm before the final view became broadly uniform near 300-370 mm. The
recording showed healthy acquisition and transport, with the main caution being
occasional large edge/range transitions that benefit from obstacle-safe
temporal filtering.

The 8x8 view selector gained Raw v2. It presents a smoothly enlarged current
frame, colours measurements below 200 mm neutral grey, and removes isolated
spatial spikes. A pixel is replaced by its neighbourhood median only when at
least four valid surrounding pixels agree within 250 mm and the candidate
differs from that median by more than 600 mm. This deliberately retains coherent
near objects, wide changes, and genuine depth edges rather than applying a
blanket blur.

The recording WeightWallTubeWall.rdbg was analysed for the angled black-wall
case. It contained 177 valid matrix frames over 43.79 seconds at 4.02 Hz, with
63-64 valid zones per frame. Normal consecutive changes were small (median 2 mm
and 95th percentile 43 mm), but the dark angled surface caused coherent groups
of upper zones to jump from the approximately 500 mm wall surface to roughly
1500-1900 mm, with occasional transitions above 3000 mm. This is a low-return
or grazing-angle depth failure affecting adjacent zones, not isolated random
noise. The isolated-pixel Raw v2 filter therefore cannot safely remove all of
it; a future surface-consistency/persistence stage is required.

The 8x8 selector gained Dark surface safe. This mode accepts nearer changes
immediately but requires a jump more than 400 mm farther to persist for three
frames before discarding a known nearer surface. It then performs two
conservative surface-repair passes: a far zone is replaced only when at least
three surrounding zones agree within 220 mm and the zone is more than 450 mm
behind their median. The limited passes can repair small coherent dark-surface
holes without flattening large genuine openings. Values below 200 mm use the
same neutral-grey display treatment as Raw v2.

serial writes already apply the required backpressure.

The follow-up Qt reproduction kept telemetry and the event loop healthy but
showed that 57-58 byte zero/read commands arrived while the 91-92 byte position
commands disappeared without acknowledgement. This isolated an additional
CH9143 long-write problem under simultaneous telemetry. Desktop transmission
now divides each newline-terminated JSON message into 20-byte UART writes with
a 3 ms inter-chunk gap, then flushes only after the full line. The Teensy parser
already accumulates until newline, so protocol content is unchanged while each
radio bridge transfer remains modest.

Paced desktop writes did not resolve the length-dependent loss: approximately
58-byte zero/read commands consistently arrived, while 91-92 byte position
commands disappeared during active telemetry. The Teensy Bluetooth UART was
therefore given 2048 bytes of persistent additional receive storage before
Serial1 starts. This prevents long newline-terminated JSON commands from
overflowing the default hardware-serial RX buffer while the main loop is busy
transmitting telemetry or definitions.

The enlarged Bluetooth receive buffer uses the Teensy-specific
HardwareSerialIMXRT interface because the generic Arduino HardwareSerial type
does not expose addMemoryForRead. BluetoothConfig and BluetoothDebugWorkflow
now preserve that concrete Serial1 type, while the Herkulex port remains a
generic hardware serial reference. The corrected firmware builds successfully.
It still needs to be uploaded through the Teensy programming USB connection
before the receive-buffer correction can affect the running robot.

Live testing after that upload confirmed that long Herkulex commands now reach
the Teensy, but exposed a separate outbound bandwidth fault. Telemetry and 8x8
TOF objects were being transmitted quickly enough to overrun the wireless
bridge: captured lines contained missing sections or the start of a TOF object
inside an unfinished telemetry object. RobotDebug now serialises each outbound
object into a complete buffer, transmits it in paced 20-byte chunks, appends its
newline only after the complete object, and flushes the completed line. The
default telemetry and 8x8 frame intervals were changed to 500 ms. This retains
all fields at two updates per second while leaving capacity for reliable
bidirectional commands.

The paced firmware was verified live through COM10 with the full Herkulex
servo 4 sequence: enter debug mode, run, zero at the current position, read the
angle, command -30 degrees, hold for 30 seconds, command +30 degrees, hold for
30 seconds, then repeat both positions and perform a final angle read. Every
zero, read, and movement command was acknowledged immediately. The desktop
event loop completed 1201 heartbeat checks, telemetry stayed continuous with a
worst observed age of approximately 0.51 seconds, the final telemetry age was
approximately 0.21 seconds, and the complete 132-second test ended with zero
protocol errors.

33. LIVE ARENA-MAP AND BLUETOOTH PROTOCOL DIAGNOSIS
===============================================================================

A stationary wall-facing live test exposed two independent causes of the
strange Arena View trails. First, the BNO055 heading moved by 8.75 degrees in
12 seconds while both encoder counts remained exactly unchanged. Applying
that apparent rotation to every range sample painted a fan even though the
chassis had not moved. Arena View now refreshes the IMU baseline but holds the
mapped heading whenever the combined encoder change is below four counts. The
status line explicitly reports when this stationary encoder lock is active.
Real turns continue to use fused BNO055 heading once the encoders show motion.

Second, isolated point-TOF or 8x8-column range spikes were being stored as
permanent free-space rays. Every mapping source now has an independent range
filter. Normal changes pass immediately and accepted values use a short
three-sample median. A jump larger than 150 mm or 35 percent must be repeated
consistently before it is admitted. This rejects a lone long return while
still allowing a genuine newly visible surface after two supporting frames.
It does not alter the raw telemetry or the dedicated 8x8 display.

A later live sample showed one point sensor alternating through 8191 mm and
another returning zero. These are invalid/sentinel readings rather than arena
distances. Point readings outside the configured 10–3500 mm mapping range are
now discarded before the temporal filter, so they cannot poison its baseline,
create a ray, or participate in the purple weight comparison.

Before these changes the stationary evidence occupied columns -74 through 36
and rows 24 through 155, including a long diagonal green scar. With the same
robot stationary after the changes, the occupied bounds reduced to columns
-29 through 34 and rows 24 through 93. The remaining short fan agrees with
the deliberately outward-pointing sensor geometry stored in the layout
editor. Regression tests cover stationary heading suppression and rejection
of a single large range jump.

The protocol-error investigation also found that keyboard driving previously
sent the full generic motor-command JSON approximately every 150 ms. That is
unnecessarily large on the half-duplex Bluetooth serial link while telemetry
and 8x8 frames are being transmitted. The GUI and firmware now use the compact
packet `{\"type\":\"drive\",\"a\":-30,\"b\":-30}` for keyboard heartbeats.
The firmware accepts it only in Debug Mode and Run state, validates both
channels, refreshes the existing 500 ms motor deadman, and avoids repeated log
traffic when the output has not changed. Key release and all GUI safety paths
still send 0/0.

The compact-drive firmware was built and uploaded successfully after the
programming USB reappeared. A six-second COM10 verification then received
continuous telemetry with zero framing or JSON errors: 80 signals, live data
from all five point TOFs, ten valid 8x8 samples at address 0x33, and a running
BNO055 fusion engine with passing self-test. The desktop application must be
restarted to load the map filters and compact keyboard packets. The next
powered driving check should watch the protocol-error counter and confirm the
arena trail remains coherent while turning.

38. MATRIX STARBURST CORRECTION
===============================================================================

A live screenshot exposed that treating all 64 matrix zones as independent
horizontal rays was geometrically wrong. Y0–Y7 represent vertical field of
view, not eight sub-bearings inside an X sector. It created many long narrow
green rays, scattered red dots and nearly 8,000 persistent cells from a
stationary robot. The raw frame in that screenshot was approximately 160–214
mm while the configured mapping minimum was 200 mm, so most of the visible
long-range evidence could not describe the current scene.

The matrix mapper now works column-by-column. It filters every raw value to the
10–3500 mm range, requires at least three valid Y pixels in an X column, uses
their median distance, and requires that median to agree across two frames
before mapping it. A valid X column paints its entire one-eighth share of the
configured horizontal FOV as a filled sector: green free cells up to the
measurement and a red arc at the measured distance. Eight sectors form a
continuous cone. Current-ray overlays are limited to the two sector boundaries
and centreline rather than 64 invented bearings.

The later user-requested lower bound is 10 mm, not 200 mm. This keeps a zero
sentinel invalid while allowing the screenshot's 160–214 mm readings to paint
a short, filled cone. Restarting the GUI or pressing Reset local map removes
the already-stored starburst. This correction is desktop-only and needs no
Teensy upload. All 28 tests passed at that stage.

The lower-limit edit was checked. ArenaView.py uses 10 mm rather than literal
zero so an invalid zero return cannot paint the map; legitimate close returns
from 10 mm upward are retained. This is the intended current behavior.

41. FLAT-PLANE 8X8 ARENA PROJECTION
===============================================================================

The 8x8 Arena View previously treated each column median as radial range. Equal
values were therefore plotted on a circular arc, making a flat plate look
curved even when it was moved squarely toward and away from the sensor.

Matrix values are now interpreted as forward depth along the sensor module's
centreline. For each horizontal bearing, the mapper converts that depth to ray
length using depth divided by the cosine of the bearing relative to the module
centreline. The free-space fill and red occupied endpoint use the same planar
geometry. Equal column depths consequently terminate at the same forward
coordinate and form a straight line perpendicular to the configured module
angle. Real measurements may still form small 10 mm steps because each column
has independent noise and the evidence grid uses 10 mm cells.

The arena-model regression test now explicitly feeds an equal 1000 mm frame,
checks all eight projected endpoints have the same forward coordinate, and
checks the expected 1150 mm world position after the module's 150 mm mounting
offset. The complete desktop suite passes all 29 tests. This is a desktop-only
mapping correction and requires an app restart, not a Teensy upload. Press
Reset local map after restarting to discard curved evidence stored by the old
projector.

42. D21 INDUCTIVE PROXIMITY INPUT
===============================================================================

The inductive proximity sensor is assigned to Teensy D21. The obsolete D11
placeholder in config.h was corrected. D21 does not conflict with the current
Bluetooth, Herkulex, motor, encoder, HX12K, I2C or TOF assignments.

A reusable DigitalInputSensor library now owns digital input setup and
debouncing. Inputs are listed in the top-level `digital_inputs` array in
debug_config.json, so additional switches or presence sensors can be added
without cluttering main.cpp. Each entry chooses a unique name, pin, active
polarity, internal pull-up setting and debounce time. Up to eight are accepted;
invalid or duplicate definitions produce a robot-side error.

The current entry is `inductive_proximity`, pin 21, active-low, pull-up enabled,
with 20 ms debounce. It publishes the debounced logical state as
`digital.inductive_proximity.detected`, the debounced electrical level as
`digital.inductive_proximity.raw_high`, and the accepted edge count as
`digital.inductive_proximity.transitions`. These appear automatically in Live
Telemetry and recordings. The Wiring Guide adds the D21 row to both fresh and
already-saved layouts while preserving user edits.

D21 is a 3.3 V-only Teensy input. A raw industrial sensor output at 5 V, 12 V or
24 V must not be attached directly. The supplied interface cable, an
optoisolator or a suitable level shifter must limit the CPU-side output to
0–3.3 V. Full commissioning steps and polarity guidance are in
PlatformIO/INDUCTIVE_PROXIMITY_WIRING.md.

The Teensy 4.0 firmware builds successfully with this input enabled. The build
uses 127320 bytes of flash code and 30208 bytes of RAM1 variables. The complete
desktop suite passes all 30 tests, including the persistent Wiring Guide
migration and an exact check of the D21 active-low/pull-up/debounce definition.
The generated embedded configuration was refreshed by the successful build.
This change requires uploading the rebuilt firmware before live D21 telemetry
will appear.

43. FRONT ULTRASOUND ON D24/D14
===============================================================================

The dual trigger/echo ultrasound interface is configured with channel A TRIG on
D14 and ECHO on D24, plus channel B TRIG on D22 and ECHO on D20 through the
8-pin cable. Live edge capture confirms this reversed-within-each-pair mapping
is the working mapping. The old D9/D10 placeholders in config.h were replaced.
D14 is also A0, so the unused IR_LEFT placeholder cannot operate at the same
time.

A reusable UltrasoundSensor library sends a 10 microsecond trigger every 100 ms
and captures both echo edges with hardware interrupts. It does not use the
example's unbounded `pulseIn()` call, so a missing echo cannot stall serial
parsing, motor deadman handling or servo service. The echo times out after 30
ms. Successful pulse duration is converted to millimetres using approximately
0.343 mm per microsecond and divided by two for the outward/return path;
20–5000 mm is the accepted range.

Ultrasound devices are now declared in the top-level `ultrasound_sensors` JSON
array. The supplied interface has A/B sockets and the workflow supports both,
but each requires its own trigger/echo pair. A scheduler permits only one
transmitter/listener pair at a time and alternates completed measurements, so
the channels cannot cross-trigger one another. Channel A publishes
`ultrasound.a.valid`, `.timed_out`, `.echo_us`, and `.distance_mm` when
valid. Channel B publishes the corresponding `ultrasound.b.*` fields. Dynamic
telemetry makes both appear in the GUI and recordings without adding
GUI-specific controls.

The Wiring Guide adds a persistent Front ultrasound board row to both new and
existing settings while retaining custom entries. Electrical and commissioning
details are in PlatformIO/ULTRASOUND_WIRING.md. D14 must never receive more than
3.3 V; condition any 5 V echo output before it reaches the Teensy.

51. ULTRASONIC ARENA-WIDTH SWEEP TERMINATION AND IMU-CONFIRMED MAP ODOMETRY
===============================================================================

This change is based on testing-branch commit 92cffc0 ("online chat made
better") and supersedes the fixed eleven-lane completion rule described in the
second section 50. The improved 200 mm lane spacing and proportional wall/
heading control from that commit are retained, but the robot no longer assumes
a known arena width or a set number of sweep passes.

Dynamic sweep width / opposite-wall detection:

- The 200 mm value is now only the nominal separation between adjacent long
  sweep passes. There is no `SWEEP_LANE_COUNT` completion condition.
- The robot begins the sweep while already running close to the first side wall
  after the 250 mm left-wall-follow phase. It then works laterally toward the
  opposite side of the arena.
- Both side ultrasound sensors are used to determine how much unmapped arena
  remains. Because the robot reverses its long-sweep heading after every lane,
  the sensor looking toward the still-unmapped side alternates naturally:
    - when the next lane shift is to robot-right, Ultrasound B/right is the
      remaining-width sensor;
    - when the next lane shift is to robot-left, Ultrasound A/left is the
      remaining-width sensor.
- Side ultrasound readings used for arena width accept the driver's full useful
  range up to 5000 mm. Each side has a filtered sweep reference. The filter is
  updated only when that ultrasonic channel completes a new echo, not once per
  main-loop iteration, so a stale sample cannot be counted repeatedly.
- A new sweep-side sample is rate-limited by 200 mm before the filtered value
  moves one third of the limited difference. This reduces the chance that one
  broad-beam reflection or spike causes premature arena completion.
- At the end of every long pass, when the forward sensors reach the end wall,
  the controller examines the ultrasonic sensor facing the still-unmapped side.
  If no valid filtered side range is available, the drivetrain remains neutral
  and waits rather than blindly making another lateral move.
- The target final side clearance is 250 mm. A +/-75 mm completion allowance is
  used, so when the remaining-side ultrasonic reports 325 mm or less at the end
  of a long pass the coverage routine enters `complete` and commands neutral.
- If more arena remains, the next shift is normally 200 mm. When less than
  200 mm of lateral travel remains before the 250 mm edge target, that final
  shift is shortened to exactly the measured remaining amount. The following
  long pass therefore runs close to the opposite wall rather than overshooting
  it. In effect the pattern goes from brushing one side of the arena to
  brushing the other without knowing the arena width in advance.
- `navigation.lane` is retained as a diagnostic count only; it no longer
  decides when mapping is finished.
- Added compact telemetry:
    - `navigation.remaining_width_mm` while a valid remaining-side reference is
      available during a sweep;
    - `navigation.next_shift_mm` for the dynamically selected lateral move.

Encoder/IMU cross-check for the virtual map:

The BNO055 does not provide a trustworthy absolute translational velocity
signal. Its linear acceleration can, however, independently confirm that the
physical chassis actually started moving. A firmware-side motion-event detector
therefore runs at the existing 50 ms IMU sample rate:

- motion start threshold: 0.22 m/s^2 for two consecutive samples (~100 ms);
- motion stop threshold: 0.08 m/s^2 for three consecutive samples (~150 ms);
- each confirmed stationary-to-moving transition increments a persistent
  `imu.motion_event_count`;
- `imu.motion_active` and `imu.motion_event_count` are included in normal
  telemetry. The event counter allows the GUI to see a short launch
  acceleration even when it occurred between slower telemetry packets.

Arena View now cross-checks encoder translation against this IMU evidence:

- encoder counts are always consumed immediately, including rejected motion,
  so false wheel movement can never be accumulated and applied later;
- when a new encoder-motion bout starts, map translation is accepted only when
  the IMU is currently valid and either `imu.motion_active` is true, the motion
  event counter has incremented, or the fused BNO055 heading has changed by at
  least 0.5 degrees (independent evidence for a real turn);
- once a bout has been confirmed, the confirmation remains latched while the
  encoders continue moving. This is necessary because a robot travelling at
  steady velocity can legitimately have approximately zero linear
  acceleration;
- when the encoders stop, the latch clears. The next encoder-motion bout must be
  independently confirmed again by the IMU;
- if the encoders move while the current IMU is invalid or supplies no motion
  evidence, Arena View leaves x/y and travelled distance unchanged, reports
  zero virtual linear speed for that sample, and displays
  `ENCODER/IMU DISAGREEMENT: map translation held.`;
- older recordings/firmware that do not contain the new `imu.motion_*` fields
  retain the legacy odometry path for replay compatibility.

52. UNEXPECTED-WALL DETOURS THAT RETURN TO THE ORIGINAL SWEEP PATH
===============================================================================

This change builds directly on section 51's dynamic arena-width sweep logic and
IMU-confirmed Arena View odometry. The robot still maps the arena with 200 mm
nominal lane spacing, still decides the final arena width from the side
ultrasound sensors, and still has no fixed sweep-lane count. The new behaviour
only changes what happens when a forward wall/obstacle appears where a normal
arena end wall is not expected.

Unexpected-wall detection:

- Completed wall-to-wall sweep legs now teach the firmware an expected long
  sweep length from the calibrated encoders.
- `navigation.sweep_progress_mm` accumulates only while the robot is actually
  travelling on its long sweep line. Temporary obstacle-detour travel is
  deliberately excluded so a bypass cannot make the learned arena length grow.
- The first clean completed sweep establishes the expected sweep length. Later
  completed sweeps low-pass update it with 75 percent previous length and
  25 percent current length.
- Once that expected length exists, a forward wall reached more than 450 mm
  before the expected end of the lane is classified as an unexpected obstacle
  rather than an arena boundary.
- The SEN0628 8x8 also provides a geometry-based obstacle cue. Each horizontal
  X column uses the median of at least three valid Y samples. An outer left or
  right flank is considered open when at least two of its three outer columns
  see farther than 550 mm.
- The 8x8 flank rule allows a localised obstacle to be recognised even before
  an expected arena length has been learned. A broad wall that fills the whole
  first-sweep field cannot be distinguished safely from the true arena end wall
  until at least one clean wall-to-wall sweep has established the arena length.

Choosing a bypass side:

- A detour is attempted only when the chosen side ultrasound reports at least
  450 mm of lateral room.
- If both sides are possible, the robot prefers the side with the greater
  measured ultrasound clearance. The 8x8 flank distance is used only as a
  tie-breaker.
- If the controller knows the wall is unexpectedly early but neither side has
  enough verified room, autonomous navigation stops rather than guessing a
  route or driving into the obstruction.

Detour path:

1. The current exact sweep heading is saved. The lane number and the normal
   B/A alternating arena-width direction are not changed.
2. The robot turns 90 degrees toward the selected bypass side.
3. It drives laterally while the ultrasound sensor facing back toward the
   obstacle tracks the obstacle edge. A right detour therefore tracks the wall
   with Ultrasound A/left; a left detour tracks it with Ultrasound B/right.
4. A side return at 650 mm or less confirms that the obstacle is actually being
   tracked. The edge is considered cleared only after two fresh ultrasonic
   measurements are clear: either timeout/open space or a valid range of at
   least 800 mm.
5. After the edge is cleared the robot continues another 220 mm for body
   clearance, records the total lateral encoder offset, then turns back onto the
   exact original sweep heading.
6. It drives forward past the obstacle, again using the obstacle-side
   ultrasound to determine when the far edge has passed. It then adds another
   220 mm forward clearance margin.
7. The robot turns 90 degrees back toward the original sweep lane and drives the
   exact measured lateral offset back using both calibrated encoders.
8. It turns back to the stored original sweep heading and resumes the same
   sweep path from beyond the obstacle. The lane counter is not incremented and
   the detour does not consume a 200 mm coverage lane shift.
9. On returning to the sweep path, the side-width filters are deliberately
   invalidated and reacquired so measurements taken while the robot was rotated
   around the obstacle cannot corrupt the remaining-arena-width estimate.

Safety limits during a detour:

- Maximum lateral search for an obstacle edge: 1200 mm.
- Maximum forward travel while waiting to pass the obstacle: 2500 mm.
- If the lateral route becomes front-blocked before the obstacle edge is found,
  the forward bypass path becomes blocked, the return path becomes blocked, or
  the obstacle never ends within the above limits, navigation stops and logs an
  explicit abort reason.
- Broad returns at approximately the learned sweep-end distance still follow
  the existing normal arena end-wall sequence and dynamic 200 mm/final-shortened
  lane-shift logic.

New navigation phases:

- `obstacle_turn_out`
- `obstacle_offset`
- `obstacle_turn_forward`
- `obstacle_pass`
- `obstacle_turn_back`
- `obstacle_return`
- `obstacle_turn_in`

Non-aborting recovery:

- Failed obstacle-detour conditions no longer call `stopNavigation()`.
- These conditions now enter a generic recovery path while autonomous
  navigation remains enabled:
  - no immediately safe detour side;
  - lateral detour path blocked;
  - obstacle edge not found within the lateral search limit;
  - forward bypass path blocked;
  - obstacle extends beyond the forward detour limit;
  - return path to the original sweep lane blocked.
- Recovery first reverses away from the failed local plan.
- The normal recovery back-off is 350 mm once at least one side has opened.
- A recovery reverse is bounded at 800 mm before a new heading is attempted.
- The new turn is chosen toward the side ultrasound reporting the most room.
  If neither side is available, successive recoveries alternate direction.
- If the new recovery heading is still blocked, the robot does not immediately
  chain another in-place turn. It reverses again first, flips the intended turn
  direction, then reassesses.

  invalidated and the robot returns to `seek_wall` so it can reacquire the

61. SENSOR-FUSED WALL MAPPING / TOF NOISE REJECTION / WALL RECLASSIFICATION
===============================================================================

This change is based on the current testing branch commit:

- 4c6459844c4bf76db0783eb0aaca71bd3bfb78bb
  "Added new internal wall recognition, not working but yk"

Affected file:

- Non-Teensy-Files/BluetoothDebugGUI/ArenaView.py

No Teensy firmware, navigation state machine, pin allocation, Bluetooth packet,
debug_config.json setting, sensor driver or recording format was changed.
Navigation controller version remains 7.

Problem addressed:

The previous wall mapper promoted range endpoints into persistent wall geometry
too quickly. A few noisy point-TOF or 8x8 returns could therefore become dashed
orange internal-wall segments. Large numbers of those false segments could make
the map look like a maze even when later free-space evidence disagreed.

The mapper now uses a staged sensor-fusion pipeline:

  raw range -> temporal validation -> occupancy/free-space evidence
            -> pending wall evidence -> confirmed wall geometry
            -> internal/external classification

1. STRONGER TEMPORAL FILTERING

- Top point-TOF sensors no longer allow their first valid sample to become wall
  geometry immediately.
- A new top-TOF baseline must be supported by three mutually-consistent samples
  before that distance is accepted for wall mapping.
- The rolling median history was increased from 3 to 5 accepted samples.
- Bottom TOFs retain their immediate behaviour because they are primarily used
  for near-floor/weight logic rather than persistent wall creation.
- Ultrasound and 8x8 columns continue to require initial confirmation before
  contributing persistent geometry.

2. PENDING WALL-EVIDENCE FUSION

- A valid range endpoint is no longer converted directly into a wall track.
- Candidate wall endpoints are accumulated into spatially-compatible evidence
  clusters first.
- Approximate geometry matching for a pending cluster requires:
  - the same horizontal/vertical orientation;
  - perpendicular coordinate agreement within roughly 120 mm;
  - longitudinal continuity within roughly 220 mm.
- Source weights are intentionally unequal:
  - temporally-confirmed point TOF: 2.0 wall-confidence units;
  - coherent 8x8 sector: 2.5 wall-confidence units;
  - ultrasound: 0.75 wall-confidence units.
- A pending cluster needs at least 4.0 confidence units and at least two accepted
  observations before becoming persistent wall geometry.
- This means ultrasound mainly corroborates geometry rather than defining a
  precise wall by itself.
- Weak stale unconfirmed clusters decay instead of remaining forever.
- Free-space rays crossing a pending endpoint reduce its confidence before it
  can become a wall.
- The last approximately 100 mm of a point-TOF ray, and approximately 140 mm of
  an 8x8 sector, are excluded from this contradiction test so centimetre-level
  endpoint quantisation cannot cancel a genuine wall.

3. 8x8 SPATIAL SENSOR FUSION

The 8x8 matrix now has two separate spatial-consensus tests before it can create
persistent wall geometry.

Vertical consistency inside one matrix column:

- At least four valid pixels are required in the column.
- A median is calculated.
- At least four pixels must remain within max(80 mm, 12 percent of range) of
  that median.
- A few isolated flying pixels therefore cannot define the complete angular
  sector.

Horizontal consistency between columns:

- A matrix column is allowed to create persistent wall evidence only when an
  immediately adjacent column reports a similar depth.
- Adjacent depths must agree within max(100 mm, 15 percent of the nearer range).
- An isolated valid-looking 8x8 column still contributes low-confidence
  occupancy information, but it cannot create an orange/red wall line.
- Coherent neighbouring columns are given stronger occupied-cell evidence and
  wall-confidence weight.

4. OCCUPANCY-GRID CONFIDENCE

- Point-TOF endpoints now add less occupied evidence per sample than before.
- Ultrasound endpoints add only weak occupied evidence because of their broad
  acoustic beam.
- Coherent 8x8 sectors add strong occupied evidence; non-coherent sectors add
  only weak evidence.
- Every valid ray still adds free-space evidence in front of the measured
  endpoint.
- The visual occupancy layer no longer paints every +1 cell bright red or every
  -1 cell green:
  - red requires occupancy evidence >= +4;
  - green requires free-space evidence <= -3;
  - low-confidence cells are rendered as the dark map background.
- This is deliberately a visual confidence threshold; the underlying evidence
  values are still retained and can strengthen or weaken later.

5. INTERNAL WALLS ARE NOW THE DEFAULT CONFIRMED GEOMETRY

- A newly-confirmed wall is initially classified as an internal wall.
- It is drawn as a dashed orange segment only after the fused evidence stage has
  confirmed it.
- A single wall seen in one direction is no longer immediately declared to be
  one of the four arena boundaries.
- This prevents a genuine internal obstacle from becoming a false outer wall
  simply because it was encountered before the real arena boundary.

6. COLLINEAR INTERNAL WALL MERGING

- Nearby internal chunks with the same orientation are merged when:
  - their perpendicular coordinates are within approximately 220 mm; and
  - the gap along the wall is no more than approximately 350 mm.
- The merged line uses the median observed perpendicular coordinate and extends
  across the combined supported longitudinal range.
- This specifically addresses runs where the same physical wall appeared as a
  long sequence of separate orange dashes.

7. AUTOMATIC INTERNAL -> EXTERNAL WALL PROMOTION

A long merged internal line can now become a solid red arena boundary when the
explored geometry supports that classification.

Current promotion requirements:

- supported wall span >= 800 mm;
- at least 6 confirmed wall observations;
- at least 5 recorded robot-trail points on one side of the line;
- no more than 1 qualifying trail point on the opposite side.

This makes external-wall classification depend on BOTH wall evidence and known
free/explored space. For example:

- a long horizontal wall with explored trajectory only below it -> north arena
  boundary;
- a long horizontal wall with explored trajectory only above it -> south;
- a long vertical wall with explored trajectory only left of it -> east;
- a long vertical wall with explored trajectory only right of it -> west.

Once a line becomes an arena boundary:

- it is drawn solid red;
- later collinear confirmed chunks within roughly 200 mm extend the same red
  boundary instead of creating more orange segments beside it;
- a farther, better-supported outer line can supersede an earlier boundary.

8. ROBOT TRAJECTORY STILL OVERRIDES RANGE EVIDENCE

The existing encoder/BNO055 translation-validation logic remains intact.
Only IMU-confirmed chassis motion can correct wall geometry.

When the robot physically traverses a location:

- the approximately 210 mm radius chassis corridor receives strong free-space
  evidence;
- pending wall evidence in the traversed corridor is deleted;
- a crossed internal wall is shortened or split around the approximately
  440 mm proven-open corridor;
- a crossed outer boundary is demoted/invalidated;
- surviving pieces of crossed geometry are marked so they cannot immediately
  promote themselves back into an arena boundary.

Therefore a noisy TOF wall that the robot later physically drives through is
still removed, while a real wall with only one genuine gap retains the wall
sections on either side of that gap.

9. MAP STATUS / DISPLAY

- Header now describes the map as sensor-fused.
- Solid red = promoted external arena boundary.
- Dashed orange = confirmed internal wall.
- Low-confidence range speckle is not drawn as a wall.
- Status now reports:
  - confirmed external boundary count;
  - confirmed internal wall count;
  - current pending/unconfirmed wall-cluster count.

- The source baseline was verified against current GitHub ArenaView.py blob:
  571eccc16b6b30abdf27b98a0b416e66af51d035
- `python -m py_compile ArenaView.py` passes.
- Synthetic ArenaModel tests pass for:
  - rapidly changing point-TOF noise producing no wall geometry;
  - repeated consistent point-TOF data becoming a confirmed internal wall;
  - one isolated 8x8 column NOT creating wall geometry;
  - adjacent coherent 8x8 columns creating wall evidence;
  - separated collinear internal segments merging into one long line;
  - a long one-sided internal line promoting to an external arena boundary;
  - later collinear segments extending the promoted external boundary instead
    of remaining separate internal-wall dashes;
  - confirmed chassis traversal carving/splitting false wall geometry.
- Full PyQt GUI regression tests were not run in this environment because PyQt6
  is not installed here.

Physical verification recommended:

1. Run Arena View with the robot stationary in front of an ordinary wall and
   confirm scattered TOF noise no longer immediately creates orange dashes.
2. Sweep the 8x8 across a broad flat wall and confirm coherent adjacent sectors
   still build wall geometry.
3. Put a genuine internal wall/box in the arena and confirm it first appears as
   dashed orange after repeated evidence.
4. Drive/sweep alongside a long arena edge and confirm its orange chunks merge
   and then promote into one solid red external boundary.
5. Deliberately drive through a previously false mapped wall location and verify
   that the contradicted section disappears/splits.
6. Keep the physical STOP control ready during autonomous testing.

New strategy 3: Pre-laid mission

- Arena View now exposes a fourth navigation strategy named Pre-laid mission.
- The operator lays out the mission before starting the robot. RUN NAVIGATION
  first applies the visible navigation tuning, plans the route, uploads the
  route to the Teensy and only then starts autonomous navigation.
- Firmware accepts two built-in GUI protocol commands without requiring new
  debug_config command definitions:
  - mission_plan_set
  - mission_plan_clear
- A mission plan contains the selected start position and start heading, a
  compact waypoint polyline, flags identifying real-weight visit waypoints and
  the roaming strategy to use after all real weights have been visited.
- A maximum of 64 uploaded mission waypoints is enforced in both the GUI and
  firmware so the command remains bounded for the Bluetooth receive buffer.

Graphical pre-laid arena editor:

- A dedicated Pre-laid mission tab now sits beside the live discovered map.
- The pre-laid arena is a fixed horizontal rectangle, 4900 mm wide by 2400 mm
  high by default.
- Two fixed home bases are drawn on the left short side:
  - green home base at the top-left;
  - blue home base at the bottom-left.
- The operator selects My home as Green or Blue. The other home base is drawn
  with a red dashed overlay and labelled NO-GO ZONE. The path planner treats
  that whole base plus robot clearance as forbidden space.
- The operator can place and drag:
  - the robot start position;
  - real weight locations;
  - dummy weight locations;
  - walls;
  - ramps;
  - tubes.
- Walls and ramps can be rotated 90 degrees with Rotate selected.
- Selected non-start items can be deleted.
- Start heading is selectable as East, South, West or North.
- The whole editable layout is persisted in QSettings under
  navigation/mission_layout so it survives GUI restarts.

Path planning and obstacle handling:

- PLAN ROUTE runs an A* grid planner in arena coordinates.
- Robot radius is derived from the visible robot-width tuning value and the
  planner safety inflation follows the visible gap-margin value.
- The arena border, opponent home base, walls, ramps, tubes and dummy weights
  are inflated by the robot footprint/safety margin and treated as no-go
  geometry.
- Real weights are goals, not obstacles.
- The planner repeatedly evaluates the remaining real weights and chooses the
  reachable next target with the lowest A* path cost, producing a complete
  route through every real weight.
- Grid paths are line-of-sight simplified before upload. This keeps waypoint
  count low while retaining obstacle clearance.
- If a start or real weight cannot be reached safely, the GUI refuses to upload
  the mission and displays a ROUTE ERROR instead of producing a dangerous path.
- Dummy weights are never marked as visit targets; they only influence path
  clearance.
- The planned route is drawn in cyan. Real-weight visit waypoints are numbered
  on the route so the planned visit order is visible before the run.

Robot path following / self correction:

- When strategy 3 starts, the Teensy aligns the user-selected arena start
  heading to the current valid BNO055 heading. It will hold the motors stopped
  until a valid IMU sample exists.
- Mission coordinates use +X to the right/east, +Y downward/south and clockwise
  positive heading, matching the graphical editor and BNO055 yaw convention.
- The Teensy maintains its own mission pose from calibrated encoder travel plus
  BNO055 heading. Encoder 1 uses the currently established inverted sign and
  encoder 2 the forward sign from the straight-run calibration.
- For every update it recomputes the bearing from the estimated robot pose to
  the active waypoint. This means the robot does not merely replay fixed motor
  timings: lateral/heading error causes the requested heading to change and the
  robot steers back toward the planned polyline.
- Heading errors above 18 degrees use a point turn. Smaller errors use the
  existing proportional differential driveOnHeading controller. Speed is
  reduced near the waypoint.
- Transit waypoints use a 120 mm arrival radius. Real-weight visit waypoints use
  a tighter 100 mm arrival radius.
- Live forward ranging remains a safety layer over the pre-laid map. If the
  robot sees an unexpected blocked path and no confirmed matrix opening, it
  holds position without aborting the mission. Once the live path clears it
  resumes and again aims at the active waypoint.

Mission completion and roaming handoff:

- Arena View includes an After weights selector with Balanced, Gap explorer and
  Conservative as fallback roaming modes.
- Every uploaded waypoint corresponding to a real weight carries a target flag.
- Firmware counts visited real-weight targets. As soon as every real weight has
  been visited, it stops the mission follower, switches navigation.strategy to
  the selected fallback roaming mode, enters seek_wall and continues with the
  existing autonomous coverage behaviour.
- The mission tab displays the live firmware mission pose and heading over the
  pre-laid arena while a run is active.
- Live status shows weights visited/total, waypoint progress and whether live
  ranging is currently holding the route.
